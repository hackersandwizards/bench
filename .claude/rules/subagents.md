# Subagents

- Delegate when: (a) a task spans 3+ files, (b) research could fill the main context, (c) multiple independent queries can run in parallel.
- One task per subagent for focused execution.
- Running unattended, say so in every subagent prompt you write. A fresh delegate inherits none of your context and will otherwise stop to ask.
- Where one colleague owns an outbound channel and another decides the case, the deciding colleague writes the records and hands the drafter the recipient, the thread, the facts, and the skill section that constrains the draft. Any other unattended run drafts its own outbound mail and hands over nothing.
- Delegating never widens scope. Name the work in the prompt: the colleague does that and no part of its own standing mandate, and anything it judges to need more goes back as a decision for the principal rather than out as work it did. The prompt cannot enforce this, since a delegate's tools come from its own definition and never from the caller's, so it is the colleague's own restraint to keep.
- A delegate sent to review credential handling reasons about it from the source, and the prompt says so: no command that reads a keychain, a credential helper or a secret store. The value is printed into a transcript nobody can unprint, and only a person can rotate what leaks.
- Fan out at most 3 subagents at a time; ask before spawning more. An unattended run sends the rest in a later batch instead of asking, never absorbing their work itself. A skill that names its own fan-out width overrides this cap for that fan-out: `/simplify` runs four and is meant to.
- Prod a fan-out that goes quiet rather than waiting on it. Ask each agent for its findings with SendMessage, then do other work instead of instrumenting a wait. Never spawn a replacement for a silent agent: the original delivers, and the replacement then describes a state that has moved. Never end a turn while a phase is still owed its report. Where an agent is gone for good, do that phase yourself rather than recording it as done. Check that SendMessage is available before fanning out at all: a fan-out you cannot prod produces nothing, and the work then runs serially in your own context.
- Stop a finished delegate's task before you stop the process it left running. Stopping the process first wakes that delegate to re-report its whole context, which has cost two 650,000-token re-sends in one evening. A stale entry costs nothing while it idles, so leave the entries of finished delegates alone and stop only processes. Read the scratch folder named in a process's command line before stopping it: a folder belonging to a live delegate is that delegate's own run, not leftover state.
- A stall, a timeout or a resumed transcript is evidence that a delegate's report is incomplete. Its commits and its working tree are a second, independent record of the run, so read them over the window and hand any contradiction back to the delegate. Reconcile every hunk against what it said it did, and count the files it opened against the files you assigned.
- A delegate reports a defect inside the window you set, so its scope is never the reach of what it found. Sweep the repository for the class before relaying it as fixed.
- Verify a claim before sending a running delegate a retraction, exactly as before sending it an instruction. A delegate mid-action has no undo, so a late retraction lands as a second instruction on finished work.
- Before putting a question to a principal, re-read what you have already told the delegate. Decide it in the instruction and say what you decided, or hold the work and ask. Never both.
- Before building or changing Claude Code artifacts (skills, rules, subagents, hooks, output styles, settings, MCP), consult the `claude-code-guide` agent or official docs. Don't guess the frontmatter or mechanics from memory. A rule asserting how the system behaves is a claim about a readable system: check it against the system before writing it, and again before leaning on one already written.
- Only work that must notice an absence earns a schedule. Deterministic work becomes a gate, and event-driven work becomes an agent the event calls. A run a person triggers at your request is your run, so say what it will do in the world when you ask for the trigger.
- A scheduled task carries only what is true because it runs on a schedule: the cadence, the colleague it delegates to, the standing approval and its limit, and the ledger that dedupes across runs. Put the procedure in a skill the task loads. Test it by deleting the task: if the work is then unrunnable by hand, the procedure sits in the wrong file. A task's identifier is immutable, so renaming one is a delete plus a create, and the new registration inherits neither its last-run time nor its tool grants.
- Name a skill for its function and a scheduled task for its job, with the task's cadence as the last segment. The function name outlives the job, so a skill that gains a second mode keeps its name while the task keeps naming only what it runs.
